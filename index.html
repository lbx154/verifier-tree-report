1. 做了什么

  1. 10-19
    发现问题。旧评审的 bad 结论不可靠：常因为评审自己加的要求判失败（如 embedding-drift-monitor 上的"有偏 MMD 估计"），而题目没提过。
  2. 10-19
    设计树。根是题目，而不是 agent 对自己工作的叙述；每条要求标来源（题面、代码注释、评审推断、agent 自定）；claim 标证据强度；要求挂"未测情形"。三轮离线迭代（v1→v3）后定型。
  3. 10-20
    接进主流程（0.14）。去掉单元划分，第一阶段直接建树；程序阶段只打树上的未测情形和只有自测的 claim；结论阶段必须对每个薄弱 claim 和失败程序给交代。树随报告存盘，下一次评审在同一棵树上更新。经验库加入"先读题"。
  4. 10-20
    闭环验证。在真实 Codex 会话里：评审 bad → agent 按 to_fix 修 → 评审 good，树原地更新；修好的工作区过 TB4 隐藏测试 15/15。
  5. 10-20
    运行时监督员（实验分支）。watch 跟踪 agent 的会话文件，每隔几步让 judge 把树长一截，本地页面实时画。Codex 从零做题时树长了 7 版，交付过 TB4 15/15。
  6. 10-20
    提效。带过来的树记着读到第几步，后续只读新步骤；树已覆盖全记录时评审跳过建树；监督员与评审共用一棵树；纯等待步骤不触发长树。同一份 42 步记录 judge 总时间 19 分钟 → 8.5 分钟。
  7. 进行中
    两种用法对比。20 份有真值的交付（8 通过、12 失败，13 个任务），分别用"评审自己建树"和"监督员分段长树后评审"各跑一遍。

6. 做不到的，以及风险

  • 树阶段不是探测器。它整理 agent 的说法并评证据强度，但四棵离线树全判 good，含两份真失败。失败要靠程序打中；程序只打树里列出的情形。
  • 评审没想到的情形不会出现在树上。mvcc-m3_M3 的 tombstone 两版都漏。
  • 样本小。3 份离线交付加 2 次真跑；20 份对比在跑。
  • 噪声。good 结论下 to_fix 仍会列"过期"的 claim；程序编号每次评审重排。
  • 监督员有成本。每长一版是一个 judge 会话（约 2 分钟）。
